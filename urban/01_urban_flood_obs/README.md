# Mini Urban Flood Digital Twin

第3回：都市浸水の観測設計と意思決定価値

「デジタルツインに基づく意思決定概論」用の、教員が操作するStreamlitデモです。
10×10の架空都市を使い、Reality → Observation → Estimation → Decision → Outcomeを「派遣を考える」モードのStage 1〜5で開示し、「観測設計を比較する」モードで観測条件の効果を比較します。
既存のMini EV Energy Digital Twinに合わせ、条件設定は左サイドバー、中央に地図、右に派遣先と結果を配置しました。「観測設計を比較する」モードの前後比較ではメイン画面全体を左右の比較に使います。詳細説明と数値表は折り畳んでいます。
名称・サイドバーの「条件設定」・上部Stage切替・地図と結果の列比率を、提示されたEVデモに揃えています。

## 起動

Python 3.11以上を使用します（動作検証：Python 3.13）。このフォルダで実行してください。

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m streamlit run app.py --server.address 127.0.0.1 --browser.gatherUsageStats false
```

ブラウザで http://127.0.0.1:8501 を開きます。停止は起動したターミナルでCtrl+C。
今回はプロジェクト直下の `.venv` に依存ライブラリを導入済みです。プロジェクト直下からは以下でも起動できます。

```sh
.venv/bin/python -m streamlit run urban_flood_observation/app.py --server.address 127.0.0.1 --browser.gatherUsageStats false
```

1280×800以上、できれば1440×900程度の投影を推奨します。720px高では補足文が画面下に回ることがあります。スマートフォン向けではありません。

## 講義での操作

| Stage | 操作 | 学生への問い |
|---|---|---|
| 1 真値と配置 | 真の浸水・重要度を切替。地図の区画をクリックして最大3区画を選ぶ。Oracleボタンで最適配置を表示 | 最も深い3区画を選べばよいか？ |
| 2 少数の観測 | 水位センサ3台だけ。手動で派遣し、結果を開示 | 観測のない地区は安全か？ |
| 3 DTで推定 | 同じ3台から全域を推定。地図で派遣先を選び、必要なら自動派遣ボタンで比較 | この滑らかな地図はどこから来たか？ |
| 4 センサ数 | 均等カバーを維持して3〜30台に変更。必要ならノイズも変更 | センサを追加したら、どの判断が変わったか？ |
| 5 配置戦略 | 台数を維持して均等・重要地区・低地の3戦略を切替 | 都市全体の把握と重要地区の判断のどちらに予算を使うか？ |
| 別モード：観測設計を比較する | 変更前を保存し、サイドバーで条件を変更。前後の地図・推定誤差・自動派遣先・被害削減を比較 | RMSEの順位と、判断による損失の順位は一致するか？ |

「派遣を考える」モードのStage 1〜5では、地図の区画全体がボタンです。クリックで派遣先を追加し、同じ区画をもう一度クリックすると解除します。3台選択中に別の区画を押しても既存の選択を維持します。変更するときは1区画を解除してください。「選択をクリア」で一括解除できます。Tab・Enter/Spaceでのキーボード選択にも対応します。
選択・赤い×・右欄の派遣先・評価指標は同じ状態を参照します。派遣先は全Stageで共通に保持し、Stage・センサ数・精度・配置戦略・豪雨ケースを変更しても変わりません。ブラウザ再読み込み・別セッションでは初期化されます。

Stage 1の「Oracleの最適配置」、Stage 3〜5の「DT推定から自動派遣」を押したときだけ、その条件の自動派遣結果で置き換えます。地図をクリックして実際に配置を変えた場合は「自分で選択した派遣結果」に切り替わります。3台上限で追加を受け付けなかったクリックでは配置も選択経緯も変わりません。

右欄には選択経緯と現在の観測条件を表示します。DT自動派遣の際は選択時の豪雨ケース・台数・戦略・σも保存し、条件変更後は「条件変更前の配置を保持中」と表示します。Oracleからの配置もその旨を表示します。結果の被害評価は常に現在の豪雨ケースに対する保持中の配置の評価です。

左サイドバー最上部の「モード」で「派遣を考える」／「観測設計を比較する」を切り替えます。中央にもモード名を表示します。比較モードではStage表示と手動派遣の操作を隠し、比較対象を「センサ数」または「配置戦略」から選びます（初期選択は配置戦略）。

1. サイドバーで比較項目を選び、出発点の値を設定して「現在の設定を『変更前』に保存」を押す。
2. 比較対象の値だけを変更する。保存した変更前は左に固定され、変更後は右で更新される。サイドバーにも変更前／変更後の値を表示する。
3. 前後それぞれの推定誤差、DT推定からの自動派遣先、実際に減らせた被害を比べる。

例：基本ケース・12台・σ=0.03m・均等配置を保存し、重要地区重点に変更します。推定誤差は0.058→0.066mに増える一方、被害削減は3.70→5.59に増えます。センサ数を比較するときは「センサ数」を選び、配置戦略を固定して、例えば3台を保存してから12台に増やします。

前後の地図は共通尺度のDT推定で、黄色の観測値と赤×の自動派遣先を重ねます。比較用地図は閲覧専用です。比較文は計算値から生成し、派遣先は3地点の集合で比較します（順番だけの違いは変更扱いにしません）。サイドバー下部の「前後で揃える条件」には、豪雨・ノイズと、比較対象でない台数または配置戦略を表示します。「共通条件を設定」でこれらを変更するか比較項目を切り替えると、変更前の保存をリセットして再保存を案内します。ノイズは今回の比較対象には含めません。

「変更前」は同じ比較項目・共通条件の間で維持され、モードを往復しても残ります。比較の保存・条件変更によって、これまで手動／ボタンで保持している派遣先を上書きしません。その配置を操作・評価する場合はサイドバーで「派遣を考える」に戻ります。前後比較には手動配置の結果を混ぜません。

前後の数値と豪雨ケースは「前後の数値表・CSV」から保存できます。

地図表示には同梱の `flood_grid/index.html` を使います。コピー・配布時には **app.pyとflood_gridフォルダを一緒に**移してください。追加ライブラリ・外部CDN・フロントエンドのビルドは不要です。

Stage 2〜5は初回には真値と実現結果を隠します。「結果を開示」を入れると評価値と真値の事後表示を選べます。開示スイッチは各Stageにあり、条件変更時もそのStageでの開示状態を維持します。
Stage 1〜3は3台・均等カバー・σ=0.03mで固定。Stage 4以降の既定値は12台です。Stage 4→5では台数・精度を引き継ぎます。派遣モードと比較モードの条件設定は独立して保持します。モードを移っても元のStageと後半用の台数・精度・戦略を保持します。初期Stageでは導入用の固定条件を表示します。
地図の区画はA01〜J10。ポンプの赤×、水位センサの黄色い観測値表示、重要度6以上の区画の橙枠を共通表示します。

## 確実に見せられる比較例

**基本：局地豪雨、12台、σ=0.03m**を選びます。いずれも同じ都市・真値・観測ノイズ実現・推定方法・3台派遣です。下表は各条件で自動派遣した参考結果です。Stage 3〜5の右欄で再現するには条件変更後に「DT推定から自動派遣」を押します。比較モードでは均等配置を保存してから重要地区重点へ変更すると、この2条件の結果を直接比較できます。

| 配置 | 全域RMSE (m) ↓ | 実現被害削減 ↑ | Oracleとの差 ↓ | 派遣先 |
|---|---:|---:|---:|---|
| 空間を均等にカバー | 0.05838 | 3.70088 | 2.08941 | E04 / E05 / F05 |
| 重要地区を重点観測 | 0.06591 | 5.59114 | 0.19916 | C08 / C09 / B08 |
| 低地を重点観測 | 0.06033 | 3.41449 | 2.37580 | H03 / F04 / G04 |

均等配置は全体誤差では勝りますが、重要地区の見落としで被害削減が劣ります。
**Best Observation for State Estimation ≠ Best Observation for Decision Making**を、同数・同精度の比較として示せます。
ここでの「Best」は提示した候補間の比較です。センサ配置の全組合せを探索した最適配置という意味ではありません。

続いて重要地区重点のσを0.10→0.03mに変更すると、RMSEは0.09954→0.06591mに改善しても、派遣先（C08 / C09 / B08）と被害削減（5.59114）は同じです。自動派遣ボタンを押して再計算した場合の比較です。
これが**Accuracy ≠ Decision Value**の別の側面です。ポンプ効果の上限と、離散的な派遣先選択があるためです。
順位逆転・同じ派遣の解説文は計算結果から生成します。別の台数や豪雨では順位が一致する場合もあり、一律の優劣は主張しません。

基本ケースではOracleは病院周辺3区画（C09 / B09 / C08）を選びます。一方「病院周辺の雨が弱い」ケースではC09 / E05 / F05となり、病院周辺と市街地に分かれます。重要度が高い地点が複数あっても、浸水の程度と削減可能量によって配分が変わる例として使えます。

## 計算モデル

### 都市と真値

1区画を等面積とする100区画の都市です。すべて架空の数値です。x,yは0〜9。

- 標高指標：`e = 0.3 + 0.7*x/9 + 0.25*cos(y/2)`
- 排水基準：`q = 0.12 + 0.06*y/9` m相当
- 地形による滞留：`p = 0.22*(max(e)-e)` m相当
- 予報からの事前推定：`h0 = max(0, 0.20 + p - q)`
- 広域降雨偏差：`b = 0.24*exp(-((x-2)^2+(y-6)^2)/16)`
- 局地降雨偏差：`l = a*exp(-((x-7.6)^2+(y-1.4)^2)/1.5)`
- 排水等の偏差：`u = 0.07*sin(0.7*x+0.45*y+scenario)`
- 真の浸水深：`h = max(0, 0.20 + b + l + p - q + u)` m

`a`は基本0.36、弱い0.12、強い0.46。ケース番号は0,1,2です。ケース変更では局地降雨の強さに加え排水偏差とノイズ実現も変わります。同じケース内で観測設計を比較してください。
地形・排水基準・重要度・事前推定は既知、実際の局地雨と排水偏差は未知とします。
水理方程式・保存則を解くモデルではなく、説明可能な静的スナップショットです。

### センサと推定

観測は `z_i = max(0, h_i + σ*ε_i)`。`ε`はケースごとの固定seed（2026+ケース番号）で生成します。
負値を0に丸めるので、σは丸める前のノイズ標準偏差であり、実現した観測RMSEではありません。
同じ地点を観測すれば同じ値を返し、配置や台数の操作で乱数を引き直しません。

配置の順序は事前の既知情報だけで決めます。既存センサを移設せず順に追加する入れ子構造です。

- 均等カバー：E05から開始し、既存点までの最短距離が最大の点を追加。
- 重要地区：重要度最大のC08から開始し、`最短距離の二乗 × 重要度` が最大の点を追加。
- 低地：標高最小点から開始し、`最短距離の二乗 × [1+5*(max(e)-e)]` が最大の点を追加。
- 同点では区画番号の小さい点を優先します。「均等」は規則格子ではなく空間被覆の貪欲配置です。

推定は「事前推定＋観測残差の空間補間」です。
`K_ij = exp(-距離²/(2*1.8²))`、`α = (K_SS + 0.01 I)^(-1)(z-h0_S)`、`h_hat = max(0, h0 + K_all,S α)`。
正則化は0.01で固定し、精度比較で推定器を変えません。真値は推定関数から読みません。遠方は事前推定に戻り、未観測をゼロとは扱いません。

### 派遣と被害

重要度は背景1に、次の3つのガウス型分布を足します。人口実数や貨幣ではなく、曝露と重要施設をまとめた架空の相対重みです。

`hill(x,y) = peak * exp(-0.5 * [((x-cx)/sx)^2 + ((y-cy)/sy)^2])`

| 地区 | 中心 (cx,cy) | 上乗せ量 peak | 広がり (sx,sy) |
|---|---|---:|---|
| 中心市街地 | (4.0,4.0) | 5.0 | (1.6,1.3) |
| 病院・避難拠点周辺 | (7.5,1.5) | 10.0 | (0.8,0.8) |
| 住宅地 | (2.0,7.0) | 3.5 | (1.5,1.2) |

`weight = 1 + 市街地のhill + 病院周辺のhill + 住宅地のhill`。各分布の裾は周囲へ滑らかにつながり、重なった部分は加算します。病院の中心が区画中心の間にあるため、離散グリッドでの重要度最大値は約8.03034です（最小約1.00004）。peakは最終的な重要度の最大値ではありません。
重要度の地図は全ケースで固定の0〜12色尺度、橙枠は6以上（5区画）。住宅地や市街地の裾は橙枠がなくても背景より高い重要度を持ちます。ホバーでは小数2桁まで表示し、計算・センサ配置には丸め前の重みを使います。


- 被害：`D(h) = Σ w_i * max(h_i - 0.10, 0)`。単位は相対被害指標。
- ポンプ1台の効果：固定時間内に担当する**1区画のみ**の水深を最大0.25m低減。
- 異なる区画に最大3台。移動時間・隣接効果・再浸水・能力差を省略。
- 各区画の削減可能量：`g_i(h) = w_i*[max(h_i-0.10,0) - max(h_i-0.25-0.10,0)]`。
- 自動派遣：推定水深での`g_i`上位3区画。同点は区画番号順。
- Oracle：真の水深での`g_i`上位3区画。独立・加算的効果のため、このモデルでは厳密な最適解。
- 実現被害削減：`D(真値) - D(派遣後の真値)`。
- Oracleとの差：`Oracleの被害削減 - 実際の派遣の被害削減`。非負、小さいほどよい。
- 推定精度：全100区画を等しく扱う`RMSE = sqrt(mean((h_hat-h)^2))`。観測地点も含みます。
- 観測なしとの比較：事前推定`h0`から派遣した場合に対する追加削減。負になる場合もあります。

地図は常に介入**前**の水深です。ポンプの×は派遣地点を示し、介入後の水深を塗っているわけではありません。被害指標は介入後を評価します。水深の色尺度はすべて0〜1mで固定です。
計算は丸める前の値で行い、表示だけ丸めます。比較モードの前後の地図・数値・比較文・CSVは、保存した条件と現在条件それぞれの`run_design()`の自動派遣結果から作ります。通常の派遣画面は保持中の派遣先に対する`evaluate()`の結果で、すべて同じ被害式を使います。

## 教材としての範囲

この教材は目標間の違いが出るように設計した例です。特定のセンサ配置が一般に優れるとの実証ではありません。
各点は固定した1つのノイズ実現です。平均性能や信頼区間ではなく、センサ追加・精度向上が常に改善を生むとは限りません。
事後の被害削減を、期待Value of Information（情報を得る前の期待価値）と呼ばないようにしてください。期待VOIには複数豪雨・複数ノイズ、適切な事後分布、情報を使わない選択を含む政策最適化が必要です。
センサ費用・運用費用も含めていないため、費用便益の最適化は扱っていません。

現実の排水ポンプ車の運用、防災上の派遣判断、避難判断には使えません。
次年度のアーキテクチャ概論では、地形・降雨→センサ→データ→推定→意思決定という層に読み替え、通信欠損・道路通行・排水網・気象レーダー等へ拡張できます。

API参照：[Streamlit Plotly表示](https://docs.streamlit.io/develop/api-reference/charts/st.plotly_chart)、[AppTest](https://docs.streamlit.io/develop/api-reference/app-testing/st.testing.v1.apptest)。

- 比較モードの変更前の保存・維持・保存し直し、前後の表示数値、共通条件・比較項目変更時のリセット、保持中の派遣先を変更しないことをAppTestで検証。

モード切替で派遣先・選択経緯・比較用保存条件が失われないこと、比較モードでStageを非表示にすること、戻ると元のStageが復元されることも検証しています。

サイドバーの検証では、比較対象だけの変更では保存を維持し、豪雨・ノイズ・固定する配置戦略や比較項目の変更時は保存をリセットすることを確認しています。
